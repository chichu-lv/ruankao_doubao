# 飞书写入与重试

安装、日常学习和恢复共用本协议。每次先读取当前项目的 `dist/deployment/project-state.json`，采用其中 `state_base` 的实际名称与标识；没有配置时先定位并保存当前用户选择的 Base。`ArchitectPass State v1` 只是默认名称，不能覆盖测试 Base 或其他已绑定名称。

1. 调用前读取当前连接器或 CLI 的帮助和字段参考，不照搬旧版本的输入/输出结构。2026-09-05 实测 lark-cli 的批量新增需要 `create_records` 包装；列表结果可能用 `data.fields` 定义列、`data.data` 保存投影行，并非标准 REST 的 `data.items`。
2. 列表结果必须根据实际返回结构解析，并读取全部分页。未识别结构、解析错误、权限错误或请求超时属于「状态未知」，绝不等于「零记录」。先检查原始响应并正确回读，不能直接重试新增。
3. 写入前同时按业务主键及稳定 `request_id` 查重；重试沿用原 request ID，不生成新 ID。已存在且内容一致则复用；已有用户画像原样保留；同主键内容冲突则先核对，不直接新增第二行。
4. 提交后记录服务端返回的 record ID，回读业务主键、内容和审计 ID。网络或解析失败时，重新按业务主键查询，确认确实不存在才补写缺失行。批量部分成功只补剩余行。
5. 审计行也按稳定 `audit_id` 查重。业务记录已经成功但审计缺失时只补审计，不能重写业务记录。
6. 初始化完成后，再执行一遍「查询 → 判断需写入差异」；预期需新增 0 行、需更新 0 行，知识点业务主键唯一。画像 1、知识点 10；资源数以当前资料导入方式为准。保存第一次与重放后的计数及结论。

已经出现重复时先列出业务主键、服务端 record ID 和重复原因。不要以“修复”为由批量清空表。学习原始事件不可丢弃；仅本次明确识别的测试重复项可以在测试授权范围内处理。

## 实际时间与时区

事件、审计、健康检查的发生时间须从执行时的系统时钟取得，例如 `datetime.now(timezone.utc).isoformat()`，不得手写当前时刻或复制示例时间。保留明确时区；本地显示用时区转换，不能只替换 UTC 偏移标签。若当前官方 CLI 字段只接受无偏移的日期文本，先确认字段/账号采用的时区，再转换后格式化，并在回执保留原始带时区时刻。未知时区先记待核验，不伪造确定的时间。
